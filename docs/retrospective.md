# 从正确性基线到提交失败：一次算子开发复盘

## 出发点

项目目标是在 Ascend C 上实现稀疏注意力候选索引筛选，先通过 correctness，再做性能。开发从赛事空模板起步，使用 AI 辅助理解 API、生成代码、整理测试和分析日志，云端命令由参赛者执行并回传结果。

## 已完成的阶段

1. 梳理 Host、Tiling、Kernel 和 ACLNN 调用关系。
2. 实现 NPU 数值基线与长度、mask、Top-k 和输出排序逻辑。
3. 在真实 910B3 上运行 RUN 部署测试。
4. 通过扩展用例发现 BF16 输出相差一个编码单位的问题，核对转换方式并实现最近偶数舍入，再通过回归测试。

历史记录显示 9 + 31 个自建 NPU 用例通过。这证明一个有限测试范围内的设备实现已跑通，不等于完整输入域或官方语义已通过。

## 为什么比赛提交没有跑通

比赛提交使用 SHARED 形式，而先前验证的是 RUN 安装包。一次官方提交在 GetWorkspaceSize 阶段失败，8 个测试点均无有效执行结果。

后续同类本地 SHARED 日志显示，自定义 Kernel 二进制和 Tiling 注册信息存在，但运行时选择了系统内置的同名 LightningIndexer Tiling。它读取了本题接口不存在的属性，导致失败。官方日志本身只有错误码，不能断言其所有细节与本地完全一致。

尝试过嵌入 Host 库资源、切换生成 ACLNN 的资源注册路径。前者仍失败，后者变成找不到匹配二进制。SDK 路径查询又返回空。最后的显式初始化探针没有回传验证结果，因此这份早期记录在该阶段停留于未解决状态，不能作为最终比赛结论。

## 哪些做法需要改进

- 应当更早用与评测一致的 SHARED 路径完成一个最小端到端用例，而不是等 RUN 的 40 个测试通过后再发现部署差异。
- 一次错误码变化不能当作修复进展；应以预期函数是否被调用、输出是否正确为验收条件。
- 反复给出单次诊断命令，让用户承担过多上传、复制和回传工作。更好的做法是提前提供一次性收集工具，并限制每条假设的验证轮次。
- AI 生成的兼容性方案必须标明实验状态；构建成功不能替代运行证据。
- 没有进入 profiling 与加速验证阶段，应明确承认，不能把调试工作包装成性能优化。

## 如果重做

先验证官方同构工程，再建立语义测试和稳定基线；记录时间与性能基准后，再依次研究多核 Query 分工、向量化、Cube 矩阵乘、分块融合和 Top-k。每次优化保留正确性回归与同环境耗时对比。这些是未来计划，并非本仓库已经完成的功能。
